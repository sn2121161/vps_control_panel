# Mac 代理下载慢：诊断与改善

日期：2026-11-09。本文不包含真实服务器地址、实际配置文件或设备凭据。

## 结论

本次直接影响下载速度的因素是：公网代理 TCP 连接有明显重传，原 CUBIC 拥塞控制反复缩小发送窗口，导致吞吐极低。换用 BBR 后，直连代理下载显著改善。

这里没有把根因归为 Mac 性能不足、面板端口或服务器 CPU 不足，也没有证明所有丢包来自某个运营商、防火墙或服务商。丢包的物理位置和责任方仍未定位；BBR 减轻其对吞吐的影响，不等于修复了线路本身。

## 复现方法

在 Mac 运行独立 Mihomo 测试进程，从服务器实时读取本机专用订阅，只在内存与权限受限的临时目录中处理凭据。使用单独本机端口，不覆盖原订阅、不修改系统代理，也不增加公开代理端口。

```sh
python3 scripts/probe_throughput.py --seconds 12 --min-mbps 5
python3 scripts/probe_throughput.py --via-ssh --seconds 12 --min-mbps 5
```

第一条直接连接正式代理；第二条保持相同客户端、协议、认证、服务端和下载目标，只把连接通过 SSH TCP 隧道送到服务端。`--ssh-host` 可指定 SSH 别名，`--core` 可指定 Mihomo 路径。

这是实时网络诊断，不是离线单元测试。默认 5Mbps 仅为识别严重低速的诊断阈值，不是两台 1080p 的完整验收标准。程序只在 HTTP 200 且窗口吞吐达标时返回成功；超时情况下仍记录实际收到的数据，不把它当成完整下载。

## 对照结果

| 顺序 | 条件 | 实测平均吞吐 | 结果 |
| --- | --- | ---: | --- |
| 1 | 原 CUBIC，直连 REALITY，12 秒 | 0.118Mbps | 未达诊断阈值 |
| 2 | 原设置，同一 REALITY 经 SSH 隧道 | 20.692Mbps | 20MB 完整下载 |
| 3 | 临时 BBR，重建监听器，12 秒 | 9.575Mbps | 窗口吞吐改善 |
| 4 | 切回 CUBIC，同样重建监听器 | 0.155Mbps | 再次低速 |
| 5 | 再次 BBR，Cloudflare | 15.384Mbps | 20MB 完整下载 |
| 6 | BBR，OVH | 11.639Mbps | 10MiB 完整下载 |
| 7 | BBR，四连接、20 秒窗口 | 19.783Mbps 合计 | 窗口吞吐达标 |
| 8 | 保存 BBR 后，原单连接复现命令 | 14.315Mbps | 20MB 完整下载，回归通过 |

四连接窗口未下载完每路预设文件，表中为窗口内合计有效吞吐，不是整文件完成速度，也不是瞬时峰值或线路绝对上限。生产环境可能有其他设备流量，测试没有中断这些设备来独占带宽。

## 支持结论的观察

- 服务器 CPU 负载低、内存有余量，未发现面板中的设备流量限制。
- 多条公网代理连接中，TCP 往返时间约 150ms，CUBIC 拥塞窗口经常仅为 2–3 个数据段，并存在明显重传。
- 相同代理经 SSH 隧道明显更快，说明客户端和服务器能够处理更高吞吐；主要问题偏向外部直连传输路径。
- BBR 试验之后再恢复 CUBIC，并同样重启，速度又下降，排除了“只是重启清除临时状态”作为主要解释。
- 实测新建连接使用了 BBR；两个测速源的完整单连接下载均显著改善。

## 实施与保护

先确认当前内核支持 BBR；只加载模块而未先修改默认算法。试验时保存原设置、安排限时自动回退，再临时改变拥塞控制并重建代理监听器。旧默认值为 CUBIC。

内核文档规定，被动连接会继承监听器的算法。因此不能只修改 sysctl 就认为运行中的监听器已经切换。测试期间短暂重启代理容器，没有重启整台服务器。

在对照证实改善后，保留 BBR，并将模块加载与 TCP 参数写入服务器本地系统配置。未改变 qdisc，没有套用大批未验证的所谓优化参数，没有更换协议、密钥、代理端口或控制台入口。

实际参数文件只保存在服务器本地，并有本地副本纳入后续应用备份白名单；公开仓库保存通用代码和本说明。该持久化配置已重新加载检查，本次未为验证持久化再重启整机。

## 验证与后续限制

原低速复现命令在 BBR 下通过，两种测速源均取得完整下载结果；结束时正式 HTTPS、管理员登录、两份初始设备订阅及服务健康再次通过检查。三个现有设备均保留，未被删除或重新生成。

自动回退任务在保留 BBR 后取消，临时客户端和 SSH 隧道随诊断进程退出，临时含凭据配置自动删除。保留的诊断脚本不含真实地址、令牌或 UUID，可用于后续回归。

这次改善使短期带宽更接近双路 1080p 所需量级，但没有完成双设备三小时、五设备高峰或 Netflix 实际播放验收，也不保证每个时段均达到标称带宽。

参考：[Linux TCP 参数及监听器继承规则](https://docs.kernel.org/networking/ip-sysctl.html#tcp-variables)、[BBR 官方项目](https://github.com/google/bbr)。
